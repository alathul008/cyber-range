# DET-020 — PowerShell Process → Network Connection Correlation

**Status:** EXECUTED / TELEMETRY VALIDATED / DETECTION IMPLEMENTED / POSITIVE + NEGATIVE VALIDATED

## Objective

Validate whether a PowerShell process creation event can be correlated with a subsequent Sysmon Event ID 3 network connection using the same Sysmon ProcessGuid.

The controlled chain was:

~~~
Sysmon Event ID 1
PowerShell process creation
        ↓
Wazuh rule 92027
        ↓
same ProcessGuid
        ↓
Sysmon Event ID 3
PowerShell TCP connection
        ↓
Wazuh rule 92101
        ↓
Custom correlation rule 100108
~~~

## Environment

- DC-01 — Windows Server 2025 Active Directory domain controller
- WAZUH-01 — Ubuntu/Wazuh security server
- DC-01 Wazuh agent: 002
- Sysmon installed on DC-01
- DC-01 Sysmon/Operational telemetry collected by Wazuh
- AD domain: corp.home.arpa
- Domain NetBIOS name: CORP
- Controlled execution account observed during validation: CORP\Administrator

The corresponding controlled Sysmon Event ID 1 used the same ProcessGuid:

~~~

ProcessId: 1232
Image: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
CommandLine: "C:\WINDOWS\System32\WindowsPowerShell\v1.0\powershell.exe" -NoProfile -Command "Invoke-WebRequest http://example.com -UseBasicParsing | Out-Null"
~~~

The Event ID 3 occurred at:

~~~
2026-09-30 06:03:24.625 UTC
~~~

This established a 4.851-second Event 1 → Event 3 relationship for the controlled process.

## Wazuh Rule Discovery

The existing Sysmon Event ID 3 rules were inspected in:

~~~
/var/ossec/ruleset/rules/0810-sysmon_id_3.xml
~~~

Relevant native rules:

- 92027 — PowerShell process spawned powershell instance, Event ID 1 telemetry.
- 92101 — PowerShell process communicating over TCP, Event ID 3 base rule.
- 92105 — destination port 135/445.
- 92106 — System process activity over SMB port.

Rule 92101 is level 0, so a normal PowerShell TCP Event 3 can be matched for correlation without necessarily becoming a standalone alert.

Wazuh was independently verified to preserve:

~~~
win.eventdata.processGuid
~~~

for Sysmon Event ID 3.

## Detection Implementation

A rollback backup was created before modification:

~~~
/var/ossec/etc/rules/local_rules.xml.det020-prechange
~~~

Custom Wazuh rule 100108 was then added:

~~~xml
<rule id="100108" level="12">
  <if_matched_sid>92027</if_matched_sid>
  <same_field>win.eventdata.processGuid</same_field>
  <if_sid>92101</if_sid>
  <description>PowerShell process creation followed by network connection with same ProcessGuid.</description>
  <group>process_network_correlation,powershell,sysmon,windows,</group>
</rule>
~~~

Configuration validation:

~~~
sudo /var/ossec/bin/wazuh-analysisd -t
~~~

Result: no configuration errors.

The Wazuh manager was restarted and verified active.

## Positive Validation

A fresh controlled PowerShell network request was executed after rule deployment:

~~~
powershell.exe -NoProfile -Command "Invoke-WebRequest http://example.com -UseBasicParsing | Out-Null"
~~~

Wazuh generated exactly one 100108 alert in the validation query.

Observed correlated Event ID 3 data:

Wazuh alert:

~~~
Timestamp: 2026-09-30T06:18:53.948+0000

~~~

The Wazuh Threat Hunting view showed one hit for agent.name:DC-01 AND rule.id:100108 during the validation window.

## Negative Validation

A separate curl.exe HTTP request was executed so the network activity was generated by a non-PowerShell process.

After the test:

~~~
sudo grep '"id":"100108"' /var/ossec/logs/alerts/alerts.json | wc -l
~~~

returned:

~~~
1
~~~

The only 100108 alert remained the earlier controlled PowerShell correlation.

Therefore the negative test did not generate an additional 100108 alert.

## Detection Assessment

**Telemetry validation: PASS**

**Correlation implementation: PASS**

**Positive validation: PASS**

**Negative validation: PASS**

**Current detection behavior:** the rule requires a prior 92027 PowerShell process-creation match, a 92101 PowerShell TCP Event 3 match, and the same win.eventdata.processGuid.

No claim is made that this detection represents malicious PowerShell network activity by itself. The validation used benign administrative/test activity.

## MITRE ATT&CK

No malicious ATT&CK technique is claimed solely from this benign validation.

The underlying native PowerShell telemetry is associated by Wazuh with PowerShell execution (T1059.001), but DET-020 itself is documented as a correlation mechanism rather than evidence of malicious behavior.

## Detection Gap / Tuning

The current rule validates process-to-network correlation using Sysmon ProcessGuid.

Further tuning may be considered later for:

- destination filtering
- network direction
- high-risk ports
- remote destination context
- process reputation/signing
- command-line context
- alert cardinality

No tuning changes are claimed as part of this validation.
